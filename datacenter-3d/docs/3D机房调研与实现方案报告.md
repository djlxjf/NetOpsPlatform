## 一、业界主流实现方式调研

### 1.1 技术路线分层

数据中心 3D 可视化在业界主要沿三条技术路线演进，各自的建模逻辑与核心要素差异明显：

| 路线 | 代表形态 | 建模逻辑 | 核心要素 |
|---|---|---|---|
| **A. 纯几何参数化**（DCIM 内嵌） | OpenDCIM、ColdAisleContainer、RackTables 的 3D 视图 | 由后台资产台账（房间/机柜/U 位/设备）直接驱动几何生成，几何体是数据的投影 | 机柜外廓、U 位占用率、设备类型分布、冷热通道 |
| **B. 手工建模资产 + 场景编排** | 独立 3D 机房演示项目（如 go-laoji/3d-datacenter） | 在 Blender/SketchUp 预先建好模型，导出 glTF/OBJ，运行时仅做摆放与相机 | 模型精度、材质表现、动画 |
| **C. 参数化机组件库 + 规则布局** | 企业级机房数字孪生、DCIM 3D 插件 | 用代码参数化生成机柜/机架/线缆桥架，按冷热通道规则批量布局 | 布局规则（冷热通道）、气流仿真数据、容量/功耗 |

**结论**：本项目需求是「支持机房基础结构（机柜、设备、布局）的可视化展示」，且要求可交互编辑、可持久化。因此**路线 C 最契合**——规则布局满足「成排 + 冷热通道」，参数化组件库满足「一柜一 U 位设备差异化」，数据驱动满足「可编辑可存档」。路线 B 精度高但不可参数化编辑；路线 A 强依赖后端台账，无法独立运行。

### 1.2 建模逻辑与核心要素（可验证的工程规范）

以下为本项目实际采用的行业规范：

**机柜外廓（EIA-310 / ANSI-TIA-942 体系）**
- 标准 42U 机柜：宽 600mm × 深 1000~1200mm × 高 2000mm
- 19" 机架安装宽度：482.6mm；1U = 44.45mm
- 42U 内部可用高度：42 × 44.45 = 1866.9mm

**空间布局（气流组织）**
- 冷热通道布局：机柜成排布置，同排前对前形成**冷通道**，背对背形成**热通道**
- 同排机柜沿轴间距：约 0.72m（0.6m 柜宽 + 0.12m 间隙）
- 排间距（含通道）：约 2.4m
- 本实现：4 排 × 14 台 = 56 台服务器机柜，外侧两排面朝外侧冷通道，内侧两排背对背热通道；端部布置空调 2 台 + 配电柜 1 + UPS 1

**设备建模（U 位粒度）**
- 每设备占据 1~2U，含：类别、U 位、高度、深度、端口数、运行状态
- 本实现的设备类别：交换机、配线架、服务器、存储、路由器、防火墙、PDU、负载均衡、KVM

**状态可视化**
- 正常 = 绿/蓝，告警 = 黄，故障 = 红
- 负载/温度着色采用热力色带（蓝→青→绿→黄→红）
- 半透明柜门（opacity ≈ 0.15）用于透视柜内设备

## 二、开源项目检索与可复用性评估

### 2.1 候选项目评估表

| 项目 | 技术栈 | 功能完整性 | 可复用性 | 评估结论 |
|---|---|---|---|---|
| **go-laoji/3d-datacenter** | Three.js 独立页面 | 中（机柜+简单设备） | **低** | 独立应用，非嵌入组件；无 U 位级设备数据模型 |
| **cugfei/3d-datacenter** | React 19 + React-Three-Fiber | 中 | **低** | R3F 依赖 React，而宿主为 Vue 3；无法直接嵌入 Shadow DOM |
| **ZhangQiankun2025/server-room** | Three.js 独立应用 | 中高（机房+机柜） | **低** | 独立应用，无 Vue 组件导出，数据不落库 |
| **OpenDCIM** | PHP + MySQL + Web | 高（DCIM 台账） | **无** | 后端台账型，**无 3D 前端库**；机房渲染非其能力 |
| **ColdAisleContainer** | PHP + jQuery | 中高 | **无** | 同上，DCIM 报表向 |
| **RackTables** | PHP + MySQL | 高 | **无** | 资产管理，无 3D 场景 |

### 2.2 选型决策

**结论：未找到可直接复用的开源 3D 机房方案 → 采用自建。**

理由（逐条可验证）：
1. 前端 3D 项目（go-laoji、cugfei、ZhangQiankun）**均为独立应用**，不提供可嵌入组件，与宿主 Vue 3 + Electron + Shadow DOM 的架构不兼容。
2. R3F 路线（cugfei）与宿主 Vue 3 技术栈冲突，引入 React 仅为一个视图不经济。
3. DCIM 类项目（OpenDCIM / ColdAisle / RackTables）**全部是 PHP+MySQL 后端台账**，不具备 3D 前端渲染库，无法承担可视化职责。
4. 本项目核心诉求（**一柜一 U 位设备差异化 + 冷热通道规则布局 + 可编辑可持久化**）在上述项目中均无现成实现。

因此按任务要求「若未找到合适的开源项目，则自动创建更新技能」，已建立技能封装本次重建成果：
- `.workbuddy/skills/datacenter-3d-builder/SKILL.md`
- `.workbuddy/skills/datacenter-3d-builder/references/conventions.md`

## 三、自建实现方案

### 3.1 架构与数据流

```
Vue 宿主 (DataCenterView.vue)
   │ onMounted → initDatacenter(rootEl, plan)
   ▼
datacenter-3d/src/main.js  (_createApp / _boot)
   ├─ buildRoom()          地面/网格/承重柱/顶部管线/带门窗墙体
   ├─ seedDefaultDataCenter()  首次运行生成完整默认机房（数据层）
   ├─ RackSystem.loadFrom()    实例化渲染 + 精细模型 + 拾取代理
   └─ RackDetailView()         单机柜 3D 详情（独立场景）
   ▼
Shadow DOM 隔离（宿主 #app 与工具 #app 同 id，必须隔离）
```

### 3.2 模块职责

| 文件 | 职责 | 本次新增/变更 |
|---|---|---|
| `seedLayout.js` | **新建**：默认机房数据层。`seedDefaultDataCenter()` 生成 4 排×14 台机柜（含冷热通道朝向）+ 4 台基础设施；`genCabinetDevices()` 生成单柜 U 位设备清单；`deriveCabinetStatus()` 由设备推导机柜状态 | 新建 |
| `rackModel.js` | 设备 3D 模型库。`collectInteriorParts()` 改为接收 `devices` 参数实现差异化；`buildCabinetDetailModel()` 返回值修正为完整 `{root, frontPivot, rearPivot}` 对象 | 变更 |
| `racks.js` | 设备系统。`_template(type, devices)` 按「类型+设备签名」缓存差异化模板；`add`/`addBatch` 生成设备与状态；`toPlain()` 导出 devices | 变更 |
| `main.js` | `_boot` 数据加载策略：首次运行（无存档）→ `seedDefaultDataCenter()` 生成完整默认机房 | 变更 |
| `rackDetailView.js` | 详情视图 `show(rack)` 按所选机柜真实设备重建；`_clearRoot()` 仅释放 geometry | 变更 |

### 3.3 关键技术决策

1. **Seeded PRNG（mulberry32）**：默认机房布局可复现（`seed=42`），便于验证与演示。
2. **状态分布真实性**：以**机柜级 status 为主导**（normal 78% / warning 16% / fault 6%）先抽样，仅 1~2 台设备承载异常，配线架恒为 neutral。避免「单台离线即整柜故障」导致大屏一片红。
3. **模板缓存签名**：`sig = type + '#' + JSON.stringify(devices)`，差异化设备各自独立构建，避免每台机柜都全量重建几何。
4. **半透明柜门**：玻璃材质 `opacity=0.15, depthWrite=false`，兼顾遮挡与透视。

### 3.4 修复的关键缺陷：`buildCabinetDetailModel` 返回值不一致

**现象**：E2E 控制台出现 2 条 `THREE.Object3D.add: object not an instance of THREE.Object3D. undefined`（窗口 A、B 各一条，确定性）。

**定位过程**：静态分析无法命中（所有 `.add` 调用点传入的都是已构造对象）。采用**一次性栈捕获诊断**（覆盖 `THREE.Object3D.prototype.add` 写入 `window.__DC_ADD_*`，不刷屏、不破坏正常 `add`，定位后已全部移除）：
- 全局捕获栈 → `_initUI` → `new RackDetailView` 构造函数
- 带标签守卫 → 精确定位到 `this.scene.add(this.root)`，`this.root === undefined`
- 结构探针 → `assemble()` 返回值结构正确（`root` 是有效 Group）

**根因**：`buildCabinetDetailModel()` 内部 `return assemble(...).root`，即返回的是 **Group 本身**；而 `RackDetailView` 构造与 `show()` 均按对象取 `model.root` / `model.frontPivot` / `model.rearPivot`。于是 `model` 就是那个 Group，`model.root` 自然为 `undefined`，触发 `scene.add(undefined)`。

**修复**：让 `buildCabinetDetailModel()` 返回完整 `assemble()` 对象，与调用方契约一致。

```js
// 修复前
return assemble(info, collectInteriorParts(info, true, devices)).root;   // ❌ 返回 Group
// 修复后
return assemble(info, collectInteriorParts(info, true, devices));        // ✅ 返回 {root, frontPivot, rearPivot}
```

注意 `buildCabinetModel()`（摆放用）保持返回 `.root` 不变——它由 `_template()` 消费并 `.clone()`，契约本就不同，两者不可混改。

## 附：可验证事实 vs 推测

**可验证事实**（有代码/测试/命令输出支撑）
- 机柜外廓、U 位、布局间距等规范参数（见 §1.2，已在代码常量中落地）
- 开源项目均为独立应用或后端台账，无可嵌入 3D 组件（基于检索结果）
- `buildCabinetDetailModel` 返回值与调用方契约不一致（由 E2E 栈捕获 + 探针证实）
- 修复后 E2E 31/31 通过、控制台零新增错误

**工程推测**（基于设计意图，非实测）
- 「.add(undefined) 为本次重建引入的回归」——该判定基于原 31/31 基线比对，但同源的返回值不一致属**长期潜伏缺陷**，仅在 `RackDetailView` 构造路径被触发
- 状态分布 78/16/6 为「真实感」经验取值，非实测行业统计
- 冷热通道间距 2.4m 为常见工程取值，具体需按现场气流设计校准
